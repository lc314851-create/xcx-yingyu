# 个人词书功能 · 设计方案

> 需求：用户上传包含单词的内容（图片 / 文本 / 粘贴），系统识别出单词后与云端词库匹配，
> 保存成**仅自己可见**的个人词书；支持自定义命名、改名、删除。

---

## 一、结论先行

| 问题 | 结论 |
|------|------|
| 好做吗 | 好做。核心逻辑（匹配 + 存 + 改名 + 删除）1~2 天可出可用版 |
| 存哪里 | **云开发数据库，新增独立集合 `userBooks`，一本词书一条文档，词数组内嵌** |
| 要不要单独建表 | **要**。但真正理由不是"权限不一样"，而是**生命周期与写入模式不一样**（见 §4） |
| 云存储文件行不行 | 适合"大 + 公开 + 只读"的官方词书（现有 28 本），不适合个人书 |
| 本地缓存行不行 | **只能当读加速，绝不能当权威存储**（见 §3.3） |
| 图片 OCR | **定为付费功能，暂缓开发**，见 §6.3 —— 依赖「类目 → 虚拟支付」两步先行 |
| 词库够用吗 | **够**。去重 16,550 词，实测词次覆盖 94~95%，见 §2.3。缺的不是量，是词形归一 |

## 二、现有可复用的资产（不用重写）

| 已有 | 位置 | 复用方式 |
|------|------|----------|
| 官方词库全量数据 | `wordbooks` 集合（**28 本 / 48,026 条记录 / 去重 16,550 词**，见 §2.1） | 直接反向匹配，取 `word/phonetic/meaning` |
| ~~词形还原线索~~ | ~~`wordbooks.lemma` 字段~~ | **不可用，见 §2.2**。该字段存的是变形类型码，不是词元 |
| 功能词标记 | `wordbooks.posTag === 'func'` | 抽词时直接当停用词过滤，不用另建停用词表 |
| 用户级进度存储 | `users` 文档内 `progress_${bookId}` | 个人词书复用同一套字段，背书流程零改动 |
| 云函数绕权限模式 | `syncUser` 已有成熟写法 | `userBooks` 的读写全部走同样模式 |
| 上传/入库参考实现 | `initWords` 的 `import` / `getWords` | 抄它的分批写入与字段裁剪 |

### 2.1 词库实际规模（2026-09-22 实测）

| 指标 | 数值 |
|------|------|
| 词书数 | 28 本 |
| 记录总数（含跨书重复） | 48,026 |
| **去重后不同单词** | **16,550** |
| 高频词标记记录数 | 26,963 |
| 释义 `meaning` 覆盖 | 16,473 / 16,550 = **99.5%** |
| 音标 `phonetic` 覆盖 | 15,011 / 16,550 = 90.7% |
| 词根 `root` 覆盖 | 37.6% |
| **例句 `example` 覆盖** | 204 / 16,550 = **1.2%** ⚠️ |
| `synonyms` / `antonyms` | **0%**（字段全空） |

### 2.2 两个必须先知道的数据坑

**坑一：`lemma` 字段是坏的，不能用来做词形还原**

实测该字段存的是**变形类型码**，不是词元：

```
'interesting' -> 'i'      'chopsticks' -> 's'
'born'        -> 'd'      'lays'       -> 'p'
'evening'     -> 'i'      'number'     -> 'r'
```

（来自 ECDICT `exchange` 字段，类型码含义：`p` 过去式 / `d` 过去分词 / `i` 现在分词 / `3` 三单 / `s` 复数 / `r` 比较级 / `t` 最高级。正确的词元应取 `0:` 前缀那一段，当前解析取错了部分。）

→ **结论：词形还原必须自己做**，见 §7.2。

**坑二：例句几乎全空（1.2%）**

去重 16,550 词里只有 204 个有例句，且这 204 个里混着 `thinner`、`canberra` 这类边角词。这意味着个人词书的单词卡**例句区会是空的**。

→ 处理选项：(a) 单词卡在无例句时隐藏该区块；(b) 用上传的原文里该词所在的句子**回填例句**（成本低、效果反而更贴）——推荐 (b)，见 §7.4。

### 2.3 匹配覆盖率实测

用真实英文语料跑了一遍"抽词 → 词形归一 → 查库"的完整链路：

| 语料 | 词次覆盖 | 词种覆盖 |
|------|---------|---------|
| App 内置金句 | 97.2% | 96.7% |
| 分级新闻 Level 1 | 94.6% | 91.1% |
| 分级新闻 Level 2 | 94.3% | 90.3% |
| 分级新闻 Level 3 | 93.5% | 88.8% |
| 小说《傲慢与偏见》全本 | 90.0% | 78.1% |

**加上不规则变形表后**（仅多一张 100 来项的映射表，零数据成本）：

| 语料 | 加表前 | 加表后 |
|------|-------|-------|
| 小说《傲慢与偏见》 | 90.0% | **94.6%** |
| 分级新闻 L1 / L2 / L3 | 94.6 / 94.3 / 93.5% | **95.1 / 95.0 / 94.0%** |
| App 内置金句 | 97.2% | **99.6%** |

**关键诊断——缺口不在"词量"，在"词形归一"：**

1. 未命中的高频词几乎全是不规则变形：`was / were / been / said / did / made / came / heard / seen / told / gone / given / began / knew / known / replied / cried`。
2. 抽查其中 92 个变形，**92 个的原形全部都在词库里**（`be / say / do / make / come / hear / see / tell / go / give / begin / know / reply / cry`）。
3. 剩下的缺口绝大多数是**专有名词**（`elizabeth / darcy / bennet / longbourn`），本就不该收进词书。

→ **结论：16,550 词对"用户上传文章生成词书"完全够用。** 词次覆盖稳定在 94~95%，真正要补的是工程（词形归一 + 不规则表），不是数据量。

**顺带发现的词库数据缺陷（与个人词书无关，但值得单独修）：**

- 最基础的 97 个英语单词里，词库缺 8 个：`an / was / were / been / did / done / has / having`
- 1,539 个词条没有音标，抽样发现里面混着脏数据，例如 `<i>a dream of red mansions</i>`、`<i>harry potter and the philosopher's stone</i>` 这类带 HTML 标签的书名，本该在导入时清洗掉

### 2.4 单篇文章能生成多厚的词书

以分级新闻 Level 3 实测（448 词次）：

```
448 词次 → 归一后命中 187 → 去掉功能词 → 146 个词入库
```

→ 按一篇 400 词的阅读材料换算，**一篇约生成 130 个词**；§5.4 的"单本 500 词"上限约合 3~4 篇文章。

## 三、存储方案对比

### 3.1 云数据库独立集合（推荐）

```
userBooks 集合（一本一条文档）
{
  _id:      "自动生成",
  _openid:  "用户 openid",        // 权限隔离的唯一依据
  bookId:   "u_7f3a2c",           // 唯一 key，必须加 u_ 前缀，见 §5.2
  name:     "我那篇经济学人",       // 可改名
  source:   "paste",              // paste | txt | (image 预留)
  rawText:  "原文……",             // 截断保存，仅用于"回看原文"
  words: [                        // 词数组内嵌
    { word: "abandon", phonetic: "/əˈbændən/", meaning: "v. 放弃", example: "", from: "cet4" }
  ],
  stats:    { total: 128, matched: 121, missed: 7 },
  createTime: ..., updateTime: ...
}
```

**为什么一本一条文档，而不是一个词一条记录**

- 官方词书是一个词一条记录（`initWords` 里 `batchSize = 20` 逐条 add），因为要分页、要按 `bookId + isHighFreq` 计数。
- 个人书不需要这些。一本 300 词的 JSON 约 30~60KB，**远低于单文档上限**。
- 收益：读 1 次拿全书（官方书要分 500/page 拉好几轮）；改名 = 1 次 update；删除 = 1 次 remove。
- 代价：超大词书会撑大文档 → 用 §5.4 的上限兜住。

### 3.2 云存储文件

现有官方词书写在 `wordbooks/{bookId}.json`，前端拿临时链接直接读，秒开。为什么个人书不这么干：

- **私密性最弱**：云存储没有"仅本人可读"的权限模型，只能靠 fileID/路径不外泄 + 服务端换临时链接。路径一旦被猜到或泄露，就是公开的。
- **改名/删除成本高**：本地没有索引的话，要列目录才知道有哪些书。
- **计费不划算**：个人书读得频繁（每次进背书页都要），走 CDN 流量反而更贵。

→ 适合放**图片原图**（2MB+ 的东西塞不进数据库），不适合放词表。

### 3.3 本地缓存（`wx.setStorageSync`）

为什么不能当权威存储：

1. 单 key 上限 1MB、整体上限 10MB。你现在已经有进度、生词本、打卡历史在占额度，几本个人词书就顶到天花板。
2. **超限是静默失败**，不抛异常。用户上传成功、下次打开发现词书没了，你还查不出原因——这是最坑的一条。
3. 换手机即失，与"用云开发让数据不丢"的产品定位直接矛盾。
4. 无法支撑后续可能的"分享给同学"。

→ **正确定位：内存态 / storage 二级读缓存，用于加速，可随时重建。**

## 四、所以：该不该单独建表？

**该建。** 但把理由说准，因为它决定了表怎么设计：

| 维度 | `wordbooks`（官方） | `userBooks`（个人） |
|------|---------------------|---------------------|
| 写入频率 | 一次性导入，基本不变 | 用户随时增删改 |
| 分词粒度 | 一词一条，48,026 条 | 一本一条，百级 |
| 所有权 | 无主（`_openid` 为空） | 有主（严格按 `_openid` 隔离） |
| 读取方式 | 分页批量 | 一次性取整本 |
| 可编辑 | 只读 | 改名 / 删词 / 整体删除 |

混在一张表里的后果：权限规则没法统一（一条要"所有人可读"，一条要"仅自己可读写"），查询要处处加 `type` 过滤，计数逻辑（`getMeta` 那种 count）会被个人数据污染。所以拆表是对的。

## 五、接口与规则设计

### 5.1 云函数：`userBook`

沿用 `initWords` 的 `action` 分发风格，一个云函数管全部操作。

| action | 入参 | 返回 | 说明 |
|--------|------|------|------|
| `create` | `name`, `desc`, `source`, `rawText` | `{ ok, bookId, name, words[], stats, missedSamples[] }` | 服务端分词 + 匹配 + 建书 |
| `list` | — | `{ books: [{bookId, name, total, createTime}] }` | 只返回元信息，不带 `words` |
| `get` | `bookId` | `{ book }` | 取整本，用于背书 |
| `rename` | `bookId`, `name`, `desc` | `{ ok }` | 只动 `name`，永不动 `bookId` |
| `remove` | `bookId` | `{ ok, progressCleared }` | 需级联清理，见 §5.3 |

**安全红线（每个 action 都要做）**

```js
const { OPENID } = cloud.getWXContext();
if (!OPENID) return { ok: false, error: 'no openid' };
// 所有读写都必须带上 _openid 约束
db.collection('userBooks').where({ bookId, _openid: OPENID })
```

绝不能只按 `bookId` 查、不校验 `_openid`——否则用户 A 构造一个 `bookId` 就能读/删用户 B 的书。

### 5.2 `bookId` 命名必须带前缀

现有进度是按 `progress_${bookId}` 存在 `users` 文档里的。如果用户把书命名成 `junior`，就会和官方词书进度**直接撞车**。

→ 规则：`bookId = 'u_' + 随机短串`（如 `u_7f3a2c`），和 `name`（用户可见的书名）彻底分开。改名只动 `name`，永不动 `bookId`。

### 5.3 删除的级联清理（最易漏）

删一本个人书，要同时清掉：

1. `userBooks` 里那条文档 ✅ 显然
2. `users` 文档里的 `progress_u_xxxxxx` 字段 ← **漏了会导致用户重新上传同名书时读到旧进度**
3. `wrongBook` 数组里所有 `from === 'u_xxxxxx'` 的词条 ← 需要给生词本条目补一个来源字段

建议：删除走云函数一次性完成，客户端不要分步调。

### 5.4 上限（保护你自己）

| 限制 | 建议值 | 理由 |
|------|--------|------|
| 单次粘贴字符数 | 20,000 | 一篇文章够用 |
| 单次候选词数 | 300 | 控制云函数耗时与数据库查询量 |
| 单本词数 | 500 | 保证文档体积可控，也符合"一篇文章的词单"的定位 |
| 每人词书数 | 20 | 防刷 |
| 每用户每日创建次数 | 10 | 免费额度防刷 |

超出时给明确文案，不要静默截断。

## 六、上传形式：现实评估

### 6.1 文本粘贴 —— 立刻可做，且应是主力入口

零成本、零资质、识别率 100%（本来就是文字）。UI 上就是一个 `textarea`。

### 6.2 文本文件 —— 可做，注意坑

- 用 `wx.chooseMessageFile` 从聊天记录选文件（微信小程序读本地文件系统受限，这是最顺的路径）。
- 用 `wx.getFileSystemManager().readFile({ encoding: 'utf-8' })` 读取。
- **坑**：Windows 记事本存的 `.txt` 常带 BOM，需 `replace(/^\uFEFF/, '')`；GBK 编码的文件读出来是乱码，建议只吃 UTF-8 并在失败时提示用户改用粘贴。

### 6.3 图片 OCR —— 已定为付费功能，暂缓开发

> **决定（2026-09-22）**：图片 OCR 不做成免费能力，**定位为付费解锁项**；在虚拟支付接入之前**不开发、不排期**。
> 免费侧继续走 §6.1 / §6.2 的「粘贴文字 + .txt 文件」两个入口，配合下面的降级引导。

**为什么定位成付费项**

同行就是这么做的——Quizlet 的「扫描文档」明确写在 Plus 付费订阅里，百词斩和欧路做 OCR 的都是企业主体。而且 OCR 是这批功能里唯一有**真实边际成本**的一项（识别按次计费），放免费侧等于让平台替用户买单。

**为什么暂缓**

它的开发依赖链是 **「类目确认 → 虚拟支付接入 → OCR」**，顺序不能倒，否则做完了也没有收款通道。所以 OCR 排在最后，不是因为它难做，而是因为它前面还欠两步。

| 路径 | 现状 |
|------|------|
| `wx.serviceMarket.invokeService` 调腾讯云 OCR | 需开通微信服务市场。此前卡在「多数 OCR 能力要求企业主体」，但 **2026-08-31 起个人主体已可完成微信认证（30 元/年）**，前提已松动，**具体可购性待确认**（见 §12.6）。资费含 100 次/天免费档，按付费功能定位后这个额度够做灰度 |
| 接百度 / 阿里 OCR | 需自建后端 + 域名备案 + API Key 保管，个人主体 + 云开发的轻量定位下成本陡增。**不推荐** |
| 小程序端本地 OCR | 微信未提供离线文字识别能力，此路不通 |

**免费侧当下的过渡做法（体验几乎无损）**

引导用户用**系统自带的「提取文字」**——微信里长按图片可直接提取文字，iOS 相机/备忘录也能，识别率比一般 OCR 还好。用户复制后粘进输入框即可。

> ⚠️ 这是**过渡方案，不是终态**。付费 OCR 上线后，这段引导要同步降级为次要路径，别让用户继续绕路。

→ 在此之前，图片在功能里的定位是「**留存入口**」（允许存一张原图作为出处），不是「识别入口」。

## 七、抽词与匹配的算法要点

### 7.1 分词（实现时改为服务端统一做）

原设计是客户端先抽词再上送 `tokens[]`，落地时**改成了服务端统一分词**，客户端只送 `rawText`。
原因：分词 + 词形归一的规则必须在两端保持一致，拆成两份实现迟早对不上。
现在 `cloudfunctions/userBook/extract.js` 是唯一的规则源，`scripts/test-userbook-extract.js` 可离线验证它。

### 7.2 服务端匹配（云函数内）

```js
// 分批查，避免 in 数组过大
const BATCH = 80;
for (let i = 0; i < tokens.length; i += BATCH) {
  const res = await db.collection('wordbooks')
    .where({ word: _.in(tokens.slice(i, i + BATCH)) })
    .field({ word: true, phonetic: true, meaning: true, example: true,
             bookId: true, isHighFreq: true, posTag: true })
    .limit(1000)
    .get();
  // ...
}
```

**必须处理的三件事**

1. **跨书重复**：同一个 `abandon` 在 cet4/cet6/postgrad 里都有，一次 `in` 查询会返回多条。
   → 按 `word` 去重，优先取 `isHighFreq === true` 的那条，并在词条上记 `from: bookId` 标明出处。
2. **功能词过滤**：查出来的词如果 `posTag === 'func'`（the / of / is / and…），**不放进个人词书**——背这些没意义。这直接复用了你现有的字段，不用另建停用词表。
3. **词形还原（本功能的真正难点，必须做）**：用户原文里的 `studies` / `running` / `was` / `children`
   和词库里的 `study` / `run` / `be` / `child` 对不上。实测不做这一步覆盖率只有 90%，做了到 95%。
   **不要用 `lemma` 字段**（见 §2.2，该字段是坏的），自己实现两层：

   **第一层：不规则变形映射表**（收益最大、成本最低，约 100 条，建议直接内置在客户端或云函数里）

   ```js
   // 覆盖 be / do / have / say / make / come / go / see / take / get / know / give … 的常见变形
   const IRREGULAR = {
     was:'be', were:'be', been:'be', am:'be', is:'be', are:'be',
     said:'say', did:'do', done:'do', has:'have', had:'have', having:'have',
     made:'make', came:'come', went:'go', gone:'go', took:'take', taken:'take',
     got:'get', seen:'see', saw:'see', heard:'hear', told:'tell', given:'give', gave:'give',
     found:'find', thought:'think', felt:'feel', left:'leave', kept:'keep', held:'hold',
     brought:'bring', sent:'send', spent:'spend', built:'build', lost:'lose', met:'meet',
     paid:'pay', ran:'run', sat:'sit', stood:'stand', understood:'understand',
     wrote:'write', written:'write', spoke:'speak', broken:'break', chose:'choose',
     drove:'drive', fell:'fall', grew:'grow', shown:'show', drawn:'draw', threw:'throw',
     led:'lead', fed:'feed', fought:'fight', caught:'catch', taught:'teach',
     sold:'sell', won:'win', wore:'wear', rose:'rise', cannot:'can',
   };
   ```

   **第二层：规则化后缀还原**（兜住规则变形）

   ```js
   function forms(w) {
     const out = new Set([w]);
     if (IRREGULAR[w]) out.add(IRREGULAR[w]);
     if (w.endsWith("'s")) out.add(w.slice(0, -2));
     if (w.endsWith('ies') && w.length > 4) out.add(w.slice(0, -3) + 'y');
     if (w.endsWith('es') && w.length > 3) { out.add(w.slice(0, -2)); out.add(w.slice(0, -1)); }
     if (w.endsWith('s') && !w.endsWith('ss')) out.add(w.slice(0, -1));
     if (w.endsWith('ing') && w.length > 4) {
       const s = w.slice(0, -3); out.add(s); out.add(s + 'e');
       if (s.length > 2 && s.at(-1) === s.at(-2)) out.add(s.slice(0, -1)); // running → run
     }
     if (w.endsWith('ed') && w.length > 3) {
       const s = w.slice(0, -2); out.add(s); out.add(w.slice(0, -1));
       if (s.length > 2 && s.at(-1) === s.at(-2)) out.add(s.slice(0, -1)); // stopped → stop
     }
     if (w.endsWith('est') && w.length > 4) out.add(w.slice(0, -3));
     if (w.endsWith('er') && w.length > 3) out.add(w.slice(0, -2));
     if (w.endsWith('ly') && w.length > 4) out.add(w.slice(0, -2));
     return out;
   }
   ```

   **执行顺序**：先用原形查一轮 → 未命中的词用 `forms()` 展开成候选集，再查一轮 → 命中的记录
   `matchedForm`（原文里的形态），方便词卡上显示"原文中是 `running`，原形 `run`"。

### 7.4 用原文回填例句（强烈建议做）

§2.2 已说明官方例句只有 1.2%。但用户上传的原文里**就有该词的上下文**——成本几乎为零：

```js
// 在原文中找该词所在的那句话，作为 example 存入
function pickSentence(text, form) {
  const sents = text.split(/(?<=[.!?])\s+/);
  const hit = sents.find(s => new RegExp(`\\b${form}\\b`, 'i').test(s));
  return hit ? hit.trim().slice(0, 160) : '';
}
```

好处：例句来自用户自己读的材料，比词典例句更贴合他的记忆锚点；而且正好填补了 98.8% 的空白。

### 7.3 未命中的词怎么办

**丢弃，但在结果页明确告诉用户**：

> 已收录 121 个词，另有 7 个未在词库中找到（如 `Zuckerberg`、`Schrödinger`）

不要静默丢弃——用户会以为功能坏了。也不要硬塞进去——没有释义，单词卡片渲染不出来。

**补充（同行调研后修订）**：给未命中的词开一个「**手动补释义**」入口。

墨墨背单词和 Quizlet 都这么做——匹配不到时提示用户自己填音标和释义。专业术语、人名、自造词恰恰是用户最想自己掌控的部分，直接丢弃会损失掉一块真实需求。
实现上给词条加一个 `custom: true` 标记，释义走用户填的值即可。

同时把解析失败的行存进 `failedLines` 字段，结果页可查看——抄墨墨的「导入记录」做法，成本极低。

同行做法的完整调研见 [`同行自定义词书功能调研.md`](./同行自定义词书功能调研.md)。

## 十一、顺带发现的词库数据缺陷

跑覆盖率实测时暴露出来的，不影响个人词书开工，但建议单独排期修：

1. **基础词缺失**：最常用的 97 个英语单词里，词库缺 8 个 —— `an / was / were / been / did / done / has / having`
2. **脏数据未清洗**：1,539 个词条没有音标，抽样发现混着带 HTML 标签的书名，如
   `<i>a dream of red mansions</i>`、`<i>harry potter and the philosopher's stone</i>`
   → 导入时过滤掉含 `<` `>` 的条目即可
3. **`lemma` 字段解析错误**：取到了 `exchange` 字段的类型码而非词元（详见 §2.2）
   → 可在 `scripts/enrich_wordbooks.py` 一处修好，重跑导入
4. **`example` 覆盖率仅 1.2%**：官方词库例句几乎空白（这也是 §7.4 建议用上传原文回填的原因）

## 十二、虚拟支付开放后的变现设计（2026-09-22 新增）

> 官方文档：https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment/person
> 2026-08-31 起，个人主体小程序可在符合条件的类目范围内开通**虚拟支付**。这直接改变了本功能的边界——"个人词书"从纯免费工具，变成可以承载增值解锁的载体。

### 12.1 同行参照：墨墨的模式

墨墨背单词把「自定义词库」直接接进了它的变现核心——**单词上限制**：新用户 600 词免费，扩容 8~163 元（550~17600 词），也可通过签到、分享、邀请免费增额。

这是同行里唯一把"自定义词库"当付费点的，值得参考，但**不要照抄"单词总量上限"**——那会惩罚重度用户，而且你现在的词库是白送的。更合适的是**按功能维度设免费额度**。

### 12.2 建议的免费/付费切分

| 能力 | 免费 | 付费解锁 |
|------|------|---------|
| 个人词书本数 | 3 本 | 不限（或 20 本上限） |
| 单本词数 | 300 词 | 1000 词 |
| 上传方式 | 粘贴文本 | .txt 文件 / **图片 OCR**（已定为付费项，见 §6.3） |
| 例句回填（§7.4） | ❌ | ✅ |
| 每日创建次数 | 5 次 | 不限 |

> 设计原则：**免费额度要够用**——让人能完整走通"传一篇文章 → 得到一本词书 → 背完"的全流程，付费点是"用得更爽"，不是"能不能用"。个人主体月限额只有 10 万元，靠的是量不是客单价。

### 12.3 ⚠️ 前提条件（未满足则整个方案不成立）

| 条件 | 状态 | 说明 |
|------|------|------|
| 个人主体 | ✅ 已满足 | 持中国大陆居民身份证 |
| **服务类目含「工具」** | ⚠️ **待确认** | 现类目为「教育 > 教育信息服务」，需追加「工具」。**这是最大卡点** |
| 小程序认证 | ❓ 待办 | 个人主体 30 元/年 |
| ICP 备案 | ❓ 待办 | 上线硬前置 |

**类目的具体风险**：个人主体开放的「工具」二级类目里，与学习工具最接近的是「信息查询」（官方举例含题库检索）与「办公」。但部分类目带排除性说明（「记账：不包含用户自定义生成内容的记录及分享」「备忘录：不涉及用户原创内容的传播及公开访问」）——**个人词书属于用户自定义内容，是否落在排除范围内需向审核侧确认**。

### 12.4 行动顺序

1. **先做 P0（`userBooks` + 云函数 + 粘贴入口）**，与类目/支付完全解耦，不等待；
2. 同时去 MP 后台确认「工具」类目能否追加——5 分钟，但决定后续路线；
3. 类目 OK → 再排 P1 虚拟支付接入（可复用 `wechat-miniprogram-virtual-pay` 技能的完整流程与验收清单）；
4. 类目不行 → 保持全免费，把个人词书当作留存功能而非变现功能。

### 12.5 图片 OCR 的定位（2026-09-22 已决策）

**决定：定为付费解锁项，暂缓开发。**

理由和完整分析见 §6.3，这里只记决策要点：

| 项 | 内容 |
|---|---|
| 定位 | 付费功能，不做成免费能力 |
| 排期 | **暂缓，不排期** —— 依赖「类目确认 → 虚拟支付接入」两步先行 |
| 免费侧替代 | 引导用户用系统自带「提取文字」后粘贴（过渡方案，非终态） |
| 技术路径 | 优先 `wx.serviceMarket` 的官方「微信OCR识别」，资费含 100 次/天免费档，够做灰度 |

### 12.6 ⚠️ 类目确认时可顺带核实的两件事

去 MP 后台看「工具」类目之前，把这两件事一起确认掉，都是一次操作的成本：

1. **服务类目能否追加「工具」** —— 决定虚拟支付与 OCR 是否可行（§12.3）
2. **微信服务市场的「微信OCR识别」认证后能否购买** —— 决定 §6.3 的技术路径是否成立

> 政策会变，这两项**不要沿用本文档的结论**，以 MP 后台实际显示为准。
